## О проекте

**Компания:** Medikamente — медицинские услуги  
**Текущее состояние:** 1 офис, 35 сотрудников, ручная обработка данных (Excel, 1C, сканы)  
**Цель:** Автоматизация процессов, обеспечение безопасности данных, поддержка 5-кратного роста

### Ключевые бизнес-цели:
1. Соответствие требованиям РФ по работе с конфиденциальными данными
2. Интеграция лаборатории анализов через API
3. Создание озера данных для BI/ML/AI
4. Разработка порталов для клиентов и сотрудников, мобильного приложения

## Task 1: Анализ безопасности системы

### Выполненные работы

1. **Выявлены конфиденциальные данные:**
   - PII (ФИО, контакты, паспортные данные)
   - PHI (медицинские данные, результаты анализов)
   - Финансовые данные (платежи, договоры)
   - Данные сотрудников

2. **Проведён аудит мер безопасности** — выявлены критические проблемы:
   - Отсутствие шифрования данных
   - Нет контроля доступа (только доменная аутентификация)
   - Нет аудита действий
   - Данные хранятся в открытом виде в Excel

3. **Созданы DFD диаграммы** для процессов:
   - Запись к врачу
   - Регистрация пациента
   - Оплата услуг
   - Ведение медкарты
   - Обработка анализов

4. **Разработан механизм тегирования данных:**
   - Формат: `{CATEGORY}:{SUBCATEGORY}:{LEVEL}`
   - Категории: `PHI`, `PII`, `FINANCIAL`, `HR`, `AUTH`
   - Уровни: L1 (критический) → L4 (низкий)

## Task 2: Проектирование решения

### Применение Privacy by Design

Архитектура спроектирована с учётом 7 принципов PbD:

| Принцип | Реализация |
|---------|------------|
| Проактивный подход | Data Classification Engine — автообнаружение PII/PHI |
| Конфиденциальность по умолчанию | IAM с RBAC/ABAC — минимальные привилегии |
| Конфиденциальность в дизайне | Шифрование на всех уровнях |
| End-to-End безопасность | Защита на всём жизненном цикле данных |
| Прозрачность | Audit Service — полное логирование |
| Уважение к пользователю | Consent Management — управление согласиями |

### Новые компоненты архитектуры

**Security Layer (Privacy by Design):**
- **API Gateway** — единая точка входа, TLS, аутентификация
- **IAM** — RBAC/ABAC, SSO, MFA
- **Data Protection Service** — шифрование AES-256, маскирование
- **Audit Service** — логирование, мониторинг, алерты
- **Consent Management** — управление согласиями ПДн

**Application Layer:**
- **Patient Portal** — веб/мобильное приложение для пациентов
- **Staff Portal** — портал для врачей и ресепшена
- **Core Services** — записи, CRM, EMR, Billing
- **Notification Service** — SMS, Push, Email

**Data Layer (Analytics с Privacy by Design):**
- **Operational DB** — PostgreSQL с TDE шифрованием
- **Classification Engine** — автоматическое тегирование данных
- **Data Warehouse** — обезличенные данные для BI/ML
- **BI Dashboard** — аналитика и отчёты

## Task 3: Оценка Data Encryption at Rest and In Transit

### Классификация данных по уровням

| Уровень | Описание | Примеры |
|---------|----------|---------|
| **L1 — Критический** | Врачебная тайна, особые категории ПДн | Диагнозы, анализы, медкарты |
| **L2 — Высокий** | Персональные данные (PII) | ФИО, паспорт, СНИЛС, контакты |
| **L3 — Средний** | Финансовые данные | Платежи, договоры, зарплаты |
| **L4 — Низкий** | Внутренние данные | Расписание, прайс-лист |

### Инструменты защиты

**At Rest (хранение):**
- PostgreSQL TDE + AES-256-GCM
- HashiCorp Vault (управление ключами)
- LUKS (шифрование дисков)

**In Transit (передача):**
- TLS 1.3 для всех соединений
- mTLS для межсервисного взаимодействия
- WireGuard VPN между филиалами

**Автоматизированный контроль:**
- pgAudit — аудит БД
- SIEM (ELK) — мониторинг
- OPA — Policy as Code
- DLP — предотвращение утечек

## Task 4: Оценка узких мест при миграции

### Диаграмма Исикавы — 6 категорий узких мест

| Категория | Ключевые проблемы |
|-----------|-------------------|
| **Инфраструктура** | Один сервер, нет отказоустойчивости, нет контейнеризации |
| **ПО** | 1С в файловом режиме, нет API, зависимость от Windows |
| **Данные** | Низкое качество Excel, нет единой схемы, PHI требует аудита |
| **Интеграции** | ККМ через OLE, нет Message Broker |
| **Персонал** | Нехватка DevOps, нехватка разработчиков |
| **Процессы** | Нет CI/CD, нет плана отката, нет мониторинга |

### Приоритетные рекомендации

1. 🔴 **P1:** Развернуть K8s, нанять DevOps, очистить данные, план отката
2. 🟠 **P2:** CI/CD, ETL-процесс, API-адаптеры, обучение
3. 🟡 **P3:** Мониторинг, Change Management, замена ККМ

## Task 5: Разработка cutover-плана

### Выбранная стратегия: Parallel Run

**Обоснование:**
- Критичность бизнес-процессов (клиника работает ежедневно)
- Защита данных пациентов (PHI) — возможность верификации
- Ограниченная экспертиза команды — время на обучение
- Простой план отката — мгновенное переключение на старую систему

### План миграции (10 недель)

| Фаза | Длительность | Описание |
|------|--------------|----------|
| **Фаза 0** | 2 недели | Подготовка: аудит, очистка данных, инфраструктура |
| **Фаза 1** | 1 неделя | Миграция данных: справочники, мастер-данные, транзакции |
| **Фаза 2** | 4 недели | Параллельная работа: пилот → 50% → 100% сотрудников |
| **Фаза 3** | 2 недели | Стабилизация: мониторинг, устранение багов |
| **Фаза 4** | 1 неделя | Отключение старой системы |

### Ключевые роли
- Руководитель проекта (Тех.директор)
- DevOps-инженер (внешний)
- DBA (внешний)
- Бизнес-аналитик (штатный)

## Task 6: Классификация данных

### Движок классификации данных (Data Classification Engine)

**Компоненты:**
- **Batch Ingestion** — приём данных из источников (Kafka Connect)
- **Schema Detector** — анализ структуры, обнаружение новых полей (Spark)
- **Pattern Matcher** — поиск PII/PHI паттернов (Regex + словари)
- **ML Classifier** — NLP для неструктурированных данных (TensorFlow)
- **Tag Repository** — хранение тегов и lineage (Apache Atlas)
- **Policy Engine** — политики защиты по тегам (OPA)
- **Router** — маршрутизация в слои хранилища (Airflow)

### Организация слоёв хранилища

| Слой | Данные | Доступ |
|------|--------|--------|
| **Raw (Bronze)** | Сырые данные | Только ETL |
| **Classified (Silver)** | С тегами | RBAC по ролям |
| **Sensitive (Gold-S)** | PHI, PII | Врачи, шифрование |
| **Analytics (Gold-A)** | Обезличенные | Аналитики, BI |
| **Public (Gold-P)** | Агрегаты | Все сотрудники |

### Метрики эффективности

- **Precision** ≥ 95% — точность классификации
- **Recall** ≥ 99% — полнота обнаружения
- **Latency** < 5 сек на 10K записей
- **Coverage** = 100% — все поля классифицированы

### Масштабируемость

- Горизонтальное масштабирование через Kubernetes
- Kafka partitions для параллельной обработки
- Sharding хранилища по региону/дате
- Auto-scaling по метрикам Queue Depth
