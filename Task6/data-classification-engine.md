# Движок классификации данных

## 1. Обзор решения

### Проблема
- Данные на входе в хранилище не размечены по классам конфиденциальности
- Структуры данных подвержены изменениям (новые поля, форматы)
- В хранилище будут храниться конфиденциальные данные (PII, PHI)
- Требуется соответствие Privacy by Design

### Решение
Движок классификации данных (Data Classification Engine) — компонент, который:
1. Автоматически обнаруживает и классифицирует данные перед загрузкой
2. Присваивает теги конфиденциальности
3. Маршрутизирует данные в соответствующие слои хранилища
4. Применяет политики защиты на основе классификации

### 2.2 Описание компонентов

| Компонент | Назначение | Технология |
|-----------|------------|------------|
| **Schema Detector** | Анализ структуры входящих данных, обнаружение новых полей | Apache Spark + Schema Registry |
| **Pattern Matcher** | Поиск паттернов PII/PHI (regex, словари) | Regexp + Reference Data |
| **ML Classifier** | Классификация неструктурированных данных | NLP модели (BERT/SpaCy) |
| **Policy Engine** | Применение политик на основе тегов | Open Policy Agent (OPA) |
| **Tag Repository** | Хранение тегов и метаданных | Apache Atlas / PostgreSQL |
| **Router** | Маршрутизация данных в слои хранилища | Apache Airflow / Kafka |

## 3. Процесс классификации данных

### 3.1 Pipeline классификации

```
Источник данных           Классификация              Хранилище
     │                          │                         │
     ▼                          ▼                         ▼
┌─────────┐   ┌──────────┐   ┌──────────┐   ┌──────────┐   ┌──────────┐
│  Batch  │──▶│  Schema  │──▶│ Pattern  │──▶│   Tag    │──▶│  Router  │
│  Input  │   │ Analysis │   │ Matching │   │ Assignment│   │          │
└─────────┘   └──────────┘   └──────────┘   └──────────┘   └──────────┘
                                                               │
                    ┌──────────────────────────────────────────┼──────┐
                    │                                          │      │
                    ▼                                          ▼      ▼
             ┌──────────┐                              ┌──────────┐ ┌──────────┐
             │ Sensitive│                              │ Analytics│ │  Public  │
             │   Layer  │                              │  Layer   │ │  Layer   │
             └──────────┘                              └──────────┘ └──────────┘
```

### 3.2 Алгоритм классификации

```python
# Псевдокод процесса классификации
def classify_data(batch):
    # 1. Анализ схемы
    schema = schema_detector.analyze(batch)
    new_fields = schema_detector.detect_changes(schema)
    
    # 2. Паттерн-матчинг для известных типов
    for record in batch:
        for field in record:
            # Проверка паттернов PII
            if pattern_matcher.is_pii(field):
                tag_repository.assign_tag(field, "PII")
            
            # Проверка паттернов PHI
            if pattern_matcher.is_phi(field):
                tag_repository.assign_tag(field, "PHI")
            
            # Проверка финансовых данных
            if pattern_matcher.is_financial(field):
                tag_repository.assign_tag(field, "FINANCIAL")
    
    # 3. ML-классификация для неизвестных полей
    for field in new_fields:
        classification = ml_classifier.predict(field)
        tag_repository.assign_tag(field, classification)
    
    # 4. Применение политик и маршрутизация
    for record in batch:
        tags = tag_repository.get_tags(record)
        layer = policy_engine.determine_layer(tags)
        router.route(record, layer)
    
    return classification_report
```

### 3.3 Паттерны для обнаружения данных

| Тип данных | Паттерн | Пример |
|------------|---------|--------|

| **Телефон** | `\+7\d{10}` или `8\d{10}` | +79001234567 |

| **СНИЛС** | `\d{3}-\d{3}-\d{3}\s\d{2}` | 123-456-789 00 |
| **Паспорт** | `\d{4}\s\d{6}` | 1234 567890 |
| **ИНН** | `\d{10}` или `\d{12}` | 1234567890 |
| **Диагноз (МКБ-10)** | `[A-Z]\d{2}(\.\d)?` | J06.9 |
| **Номер карты** | `\d{4}[\s-]?\d{4}[\s-]?\d{4}[\s-]?\d{4}` | 4111-1111-1111-1111 |

## 4. Организация слоёв в хранилище данных

### 4.1 Архитектура слоёв (Medallion Architecture + Security Layers)

```
┌─────────────────────────────────────────────────────────────────────────┐
│                         DATA LAKE / WAREHOUSE                          │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│  ┌─────────────────────────────────────────────────────────────────┐   │
│  │                      RAW LAYER (Bronze)                         │   │
│  │  • Сырые данные без обработки                                   │   │
│  │  • Краткосрочное хранение (7-30 дней)                          │   │
│  │  • Шифрование: AES-256                                          │   │
│  │  • Доступ: только ETL-процессы                                  │   │
│  └─────────────────────────────────────────────────────────────────┘   │
│                              │                                          │
│                              ▼                                          │
│  ┌─────────────────────────────────────────────────────────────────┐   │
│  │                    CLASSIFIED LAYER (Silver)                    │   │
│  │  • Очищенные и классифицированные данные                       │   │
│  │  • Теги присвоены                                               │   │
│  │  • Шифрование на уровне полей (PHI, PII)                       │   │
│  │  • Доступ: RBAC по ролям                                       │   │
│  └─────────────────────────────────────────────────────────────────┘   │
│                              │                                          │
│          ┌───────────────────┼───────────────────┐                     │
│          ▼                   ▼                   ▼                     │
│  ┌──────────────┐   ┌──────────────┐   ┌──────────────┐               │
│  │  SENSITIVE   │   │  ANALYTICS   │   │   PUBLIC     │               │
│  │    LAYER     │   │    LAYER     │   │    LAYER     │               │
│  │   (Gold-S)   │   │   (Gold-A)   │   │   (Gold-P)   │               │
│  ├──────────────┤   ├──────────────┤   ├──────────────┤               │
│  │ PHI, PII     │   │ Обезличенные │   │ Агрегаты,   │               │
│  │ полные данные│   │ K-anonymity  │   │ справочники │               │
│  │ AES-256+HSM  │   │ Псевдонимы   │   │ Без шифр.   │               │
│  │ Врачи только │   │ Аналитики,BI │   │ Все         │               │
│  └──────────────┘   └──────────────┘   └──────────────┘               │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

### 4.2 Описание слоёв

| Слой | Данные | Шифрование | Доступ | Срок хранения |
|------|--------|------------|--------|---------------|
| **Raw (Bronze)** | Сырые данные из источников | AES-256 (диск) | ETL-процессы | 7-30 дней |
| **Classified (Silver)** | Очищенные, с тегами | AES-256 + TDE | RBAC по ролям | 1-3 года |
| **Sensitive (Gold-S)** | PHI, PII — полные данные | AES-256 + HSM | Врачи, авторизованные | По требованию закона |
| **Analytics (Gold-A)** | Обезличенные данные | TDE | Аналитики, BI | 3-5 лет |
| **Public (Gold-P)** | Агрегаты, справочники | Нет | Все сотрудники | Бессрочно |

### 4.3 Дополнительные меры защиты

| Мера | Описание | Применение |
|------|----------|------------|
| **Field-Level Encryption** | Шифрование отдельных полей (ФИО, диагноз) | Sensitive Layer |
| **Dynamic Data Masking** | Маскирование при запросе (***-***-1234) | Analytics Layer |
| **K-Anonymity** | Обезличивание (минимум K записей с одинаковыми атрибутами) | Analytics Layer |
| **Tokenization** | Замена PII на токены | Все слои при передаче |
| **Row-Level Security** | Ограничение доступа к строкам по атрибутам | Sensitive Layer |
| **Audit Logging** | Логирование всех запросов к данным | Все слои |

## 5. Метрики эффективности классификации

### 5.1 Метрики качества классификации

| Метрика | Описание | Целевое значение | Формула |
|---------|----------|------------------|---------|
| **Precision** | Точность классификации (доля верных положительных) | ≥ 95% | TP / (TP + FP) |
| **Recall** | Полнота (доля найденных конфиденциальных данных) | ≥ 99% | TP / (TP + FN) |
| **F1-Score** | Гармоническое среднее Precision и Recall | ≥ 97% | 2 × (P × R) / (P + R) |
| **False Positive Rate** | Доля ложных срабатываний | ≤ 5% | FP / (FP + TN) |
| **Coverage** | Доля классифицированных полей | 100% | Classified / Total |

### 5.2 Операционные метрики

| Метрика | Описание | Целевое значение |
|---------|----------|------------------|
| **Classification Latency** | Время классификации одного батча | < 5 сек на 10K записей |
| **Throughput** | Записей в секунду | ≥ 10,000 RPS |
| **Queue Depth** | Глубина очереди необработанных данных | < 1000 |
| **Error Rate** | Доля ошибок при обработке | < 0.1% |
| **Schema Change Detection Time** | Время обнаружения новых полей | < 1 мин |

### 5.3 Метрики безопасности

| Метрика | Описание | Целевое значение |
|---------|----------|------------------|
| **Unclassified Data Rate** | Доля неразмеченных данных в хранилище | 0% |
| **Policy Violation Rate** | Нарушения политик доступа | 0 |
| **Data Leakage Incidents** | Утечки конфиденциальных данных | 0 |
| **Audit Coverage** | Покрытие аудитом операций | 100% |

## 6. Масштабируемость системы (Scalability)

### 6.1 Стратегия масштабирования

| Компонент | Тип масштабирования | Механизм |
|-----------|---------------------|----------|
| **Schema Detector** | Горизонтальное | Kubernetes pods, auto-scaling |
| **Pattern Matcher** | Горизонтальное | Spark workers |
| **ML Classifier** | Горизонтальное + GPU | Kubernetes + GPU nodes |
| **Policy Engine** | Горизонтальное | OPA replicas |
| **Router** | Горизонтальное | Kafka partitions |
| **Storage** | Горизонтальное | Sharding по дате/региону |

### 6.3 Сценарии масштабирования

| Сценарий | Триггер | Действие |
|----------|---------|----------|
| Рост объёма данных в 5x | Queue Depth > 5000 | +3 Classifier nodes |

| Рост пользователей | API Latency > 500ms | +2 Policy Engine replicas |
| Новые типы данных | Schema changes detected | Retrain ML model |

## 7. Интеграция с Privacy by Design

| Принцип PbD | Реализация в движке классификации |
|-------------|-----------------------------------|
| **Проактивный подход** | Автоматическое обнаружение новых конфиденциальных полей |
| **Конфиденциальность по умолчанию** | Все данные считаются конфиденциальными до классификации |
| **Встроенная защита** | Шифрование и контроль доступа на уровне слоёв |
| **Полная функциональность** | Данные доступны для аналитики в обезличенном виде |
| **End-to-End безопасность** | Классификация и защита на всём жизненном цикле |
| **Прозрачность** | Audit log всех операций классификации |
| **Уважение к пользователю** | Минимизация хранения PII, право на удаление |
