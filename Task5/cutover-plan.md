# Cutover-план миграции системы Medikamente

## 1. Анализ текущей ситуации

### Текущая система (As-Is)
- Монолитная архитектура на Windows Server 2022
- 1С Бухгалтерия и 1С Торговля в файловом режиме
- Данные в Excel, PDF, JPG на файловом сервере
- ККМ через OLE-компонент
- 35 сотрудников, 1 офис

### Целевая система (To-Be)
- Микросервисная архитектура
- PostgreSQL с шифрованием
- API Gateway, IAM, RBAC/ABAC
- Порталы для клиентов и ресепшена
- Интеграция с лабораторией анализов

### Бизнес-ограничения
- Непрерывность работы клиники (нельзя останавливать приём пациентов)
- Критичность медицинских данных (PHI)
- Ограниченный IT-штат (3 человека)
- Планируется расширение (новые филиалы)

## 2. Выбор стратегии миграции

### Сравнение вариантов

| Критерий | High-Level Design | Parallel Run | Branch by Abstraction |
|----------|-------------------|--------------|----------------------|
| Сложность | Высокая | Средняя | Высокая |
| Риск простоя | Высокий | Низкий | Средний |
| Время миграции | Короткое | Длительное | Среднее |
| Требования к команде | Высокие | Средние | Высокие |
| План отката | Сложный | Простой | Средний |
| Стоимость инфраструктуры | Низкая | Высокая (2 системы) | Средняя |

### Выбранная стратегия: Parallel Run ✅

**Обоснование выбора:**

1. **Критичность бизнес-процессов**
   - Клиника работает ежедневно, остановка недопустима
   - Parallel Run позволяет работать на старой системе пока новая не стабилизируется

2. **Защита данных пациентов (PHI)**
   - Параллельная работа позволяет верифицировать миграцию данных
   - Возможность сравнения результатов двух систем

3. **Ограниченная экспертиза команды**
   - IT-отдел (3 человека) не имеет опыта микросервисов
   - Parallel Run даёт время на обучение без давления

4. **Простой план отката**
   - При проблемах — мгновенный откат на старую систему
   - Нет риска потери данных

**Ограничения выбранной стратегии:**
- Требуется двойная инфраструктура на период миграции
- Необходима синхронизация данных между системами
- Увеличенные расходы на поддержку двух систем

## 4. План отката (Rollback Plan)

### Триггеры для отката

| Триггер | Описание | Порог |
|---------|----------|-------|
| Критические ошибки | Потеря данных, некорректные расчёты | Любой случай |
| Недоступность системы | Downtime новой системы | > 2 часов в рабочее время |
| Массовые жалобы | Невозможность работы для сотрудников | > 30% персонала |
| Нарушение безопасности | Утечка или компрометация данных | Любой случай |

### Процедура отката

| Шаг | Действие | Ответственный | Время |
|-----|----------|---------------|-------|
| 1 | Принятие решения об откате | Тех.директор + руководство | 15 мин |
| 2 | Уведомление всех пользователей | Сисадмин | 5 мин |
| 3 | Переключение на старую систему | DevOps | 30 мин |
| 4 | Синхронизация новых данных в старую систему | DBA | 1-2 часа |
| 5 | Верификация работоспособности | Все отделы | 1 час |
| 6 | Анализ причин и планирование исправлений | Команда проекта | 1 день |

**Максимальное время отката: 4 часа**
